# RURO Methods And Pipeline Manual v1

**Purpose:** self-contained A-to-Z guide to what this RURO/MNL project does,
how the data are prepared, how alternatives are generated, how preferences and
opportunities are estimated, and what must be validated before results are used.

**Current truth:** this repository is still a research codebase first. The
production workflow is script-based and lives mainly in `scripts/enhanced/` and
`scripts/Job_model/`. The package skeleton in `src/mnl/` is not yet the
production estimator.

**Current empirical scope:** France 2016 is the active implemented country/year.
The design goal is country/year portability, but the production code is not yet
fully country/year-agnostic.

---

## 1. What RURO Means In This Project

RURO means Random Utility Random Opportunity.

The project estimates labour-supply choices when the choice set is sampled or
constructed rather than treated as a complete deterministic menu. A household
chooses among a finite set of alternatives. Each alternative contains labour
supply variables, a tax-benefit outcome from EUROMOD, and proposal-density terms
that describe how the alternative was generated.

The estimated choice index is:

```text
V_hj = U_hj(preferences)
     + O_hj(opportunities)
     - log_prior_hj
```

where:

- `U_hj` is preference utility from consumption and leisure;
- `O_hj` contains hours, wage, market, job, or occupation opportunity terms;
- `log_prior_hj` is the proposal correction for sampled alternatives.

The proposal correction is essential. The model estimates structural preference
and opportunity components from alternatives that were generated by a proposal
distribution. The likelihood therefore subtracts the proposal log-density
exactly once.

There are two active empirical branches.

### Continuous RURO

The continuous branch draws hours and wages directly.

Main scripts:

- `scripts/enhanced/enh_france_data_prep.py`

- `scripts/enhanced/enh_RURO_draws.py`
- `scripts/enhanced/enh_RURO_euromod.py`

```text

combined_draws_em.parquet
fr_2016_RURO_mnl__singles.parquet
fr_2016_RURO_mnl__couples.parquet
```

The Stijn-style occupation baseline belongs to this branch.

### Job-Choice RURO

The job-choice branch builds a discrete job universe, draws job bundles, and
then estimates preference and market-opportunity terms from those job draws.

Main scripts:

- `scripts/Job_model/enh_job_universe.py`
- `scripts/Job_model/enh_job_draws.py`
- `scripts/Job_model/run_job_ruro_pipeline.py`
- shared downstream scripts in `scripts/enhanced/`

Typical generated files:

```text
job_universe_2016.parquet
job_universe_2016__meta.json
singles_RURO_ready_jobdraws.parquet
couples_RURO_ready_jobdraws.parquet
fr_2016_RURO_mnl_job_gmm__singles.parquet
fr_2016_RURO_mnl_job_gmm__couples.parquet
```

The current strongest empirical candidate is the pruned job-choice model:

```text
scripts/enhanced/estimation_spec_job_M2h_pruned.yaml
```

This is empirically useful but not the same object as Stijn's continuous
hours/wage opportunity model.

## 3. Current Claims And Limits

The code can estimate separate preference and opportunity parameter blocks.
That is not the same as proving structural identification.

Current defensible statement:

```text
The code implements a RURO likelihood with separate preference and opportunity
components. On the French 2016 data, the job-choice branch is the strongest
current empirical candidate. The continuous branch is structurally closest to
Stijn's implementation, but the older continuous files need further diagnostics
and, for the Stijn occupation baseline, a data rebuild before interpretation.
```

Claims to avoid for now:

- "Preferences and opportunities are fully separately identified."
- "The package is already country/year-agnostic."
- "The continuous Stijn occupation baseline is ready before the rebuild canary
  passes."


Key labour columns:

```text
lhw
hours

hours_female
wage
wage_male
wage_female
working
working_male
working_female
working_pt1
working_pt2
working_ft
```

Key occupation columns:

```text
loc
loc4
loc4_male
loc4_female
loc4_2
loc4_3
loc4_4
```

Occupation sentinels:

```text
loc4 = -1  non-worker or non-work alternative
loc4 = -2  working observed row with unknown/invalid occupation
loc4 = 1   routine-manual reference group
loc4 = 2   nonroutine-manual
loc4 = 3   routine-cognitive
loc4 = 4   nonroutine-cognitive
```

`loc4 = -2` is not an occupation. It may remain on observed working rows
(`draw = 0`) when the original occupation cannot be classified. The Stijn M0
occupation layer uses only the dummies for `loc4 = 2`, `3`, and `4`, so
`loc4 = -2` contributes zero to `O^Occ`. Simulated working alternatives must
draw only valid `loc4` values in `{1, 2, 3, 4}`.

Key budget columns:

```text
ils_dispy
ils_dispy_em
consumption
c_norm
leisure
l_norm
l_norm_male
l_norm_female
```

Key proposal and prior columns:

```text

log_q_E
log_q_H
log_q_W
log_q_Occ
log_q_E_male

log_q_Occ_male

log_q_H_female
log_q_W_female
```

The estimator should only see this canonical schema. Country/year-specific raw

## 6. Stage A: France Data Preparation

Script:

```text
scripts/enhanced/enh_france_data_prep.py
```

Purpose:

- read raw France EUROMOD/SILC data;
- harmonize identifiers and demographic variables;
- construct analysis-ready singles/couples files;
- export processed parquet files.

Typical command:

```powershell
python .\scripts\enhanced\enh_france_data_prep.py `
  --year 2016 `
  --raw-dir "Z:/hisham/EUROMOD-STORAGE/Data/raw" `
  --out-dir "Z:/hisham/EUROMOD-STORAGE/Data/processed/fr/2016" `
  --system-year 2015 `
  --export-format parquet
```

Main cleaning concepts:

- keep and harmonize household/person identifiers;
- preserve household weights for descriptives;
- split or prepare household types needed by RURO;
- check basic data quality such as impossible hours or wages;
- preserve EUROMOD variables required downstream.

This stage is France-specific today. A country/year-agnostic package would move
the raw-name mapping into a country/year config file.

## 8. Stage C: Opportunity Draws

Continuous script:

```text
scripts/enhanced/enh_RURO_draws.py
```

Purpose:

- generate observed and simulated alternatives;
- draw non-work, hours, wages, and optionally occupation;
- record proposal-density terms.

Typical continuous command:

```powershell
python .\scripts\enhanced\enh_RURO_draws.py `
  --singles-path "Z:/hisham/EUROMOD-STORAGE/Data/processed/fr/2016/singles_RURO_ready.parquet" `
  --couples-path "Z:/hisham/EUROMOD-STORAGE/Data/processed/fr/2016/couples_RURO_ready.parquet" `
  --n-draws 99 `
  --wage-spec vw `
  --h-min 5.0 `
  --h-max 70.0 `
  --w-min 2.0 `
  --w-max 170.0 `
  --rng-seed 17
```

For the Stijn occupation baseline, the key draw command change is:

```powershell
--occ-spec empirical --occ-strata __all__
```

This makes occupation vary across working alternatives rather than copying each
person's observed occupation into every working draw.

Important continuous draw outputs:

```text
singles_RURO_ready_RURO_draws.parquet

couples_RURO_ready_RURO_draws.parquet
couples_RURO_ready_RURO_draws__drawsmeta.json
```

The metadata sidecar must be passed to MNL prep when available so proposal
parameters are synchronized with the actual draw distribution.

```text

fr_2016_RURO_mnl__couples.parquet
fr_2016_RURO_mnl__mnlmeta.json
```

For the Stijn occupation baseline, the final files must contain:

```text
loc4
loc4_male
loc4_female
log_q_E
log_q_H
log_q_W
log_q_Occ
log_q_E_male
log_q_H_male
log_q_W_male
log_q_Occ_male
log_q_E_female
log_q_H_female
log_q_W_female
log_q_Occ_female
```

The prior convention is:

```text
prior > 0
log_prior = log(prior)
```

For singles:

```text
log_prior = log_q_E + working * (log_q_H + log_q_W + log_q_Occ)
```

For couples:

```text
log_prior = log_prior_male + log_prior_female
```

where each partner's log prior has the same factorized form.

## 15. Required Validation Gates

Before estimation:

1. Input files load.
2. Required columns exist.
3. Draw metadata matches the draw command.
4. `loc4` varies within household across working alternatives for Stijn M0.
5. Proposal aliases exist.
6. `prior > 0`.
7. `log_prior == log(prior)`.
8. Per-layer prior reconstruction holds.


## 17. Country/Year Portability

The target package architecture is country/year-agnostic. The current
production scripts are not fully there yet.

What should become generic:

- utility functions;
- opportunity block evaluation;
- proposal correction;
- YAML spec parsing;
- estimation engines;
- post-estimation diagnostics;
- validation gates.

What remains country/year-specific:

- raw EUROMOD/SILC column names;
- data cleaning and eligibility rules;
- education mappings;
- occupation mappings;
- region mappings;
- EUROMOD system and dataset names;
- external labour-market shifters such as GSUR;
- data paths and storage roots.

The right package design is:

```text
raw country/year data
  -> country/year harmonizer
  -> canonical RURO schema
  -> generic RURO draw/MNL/estimation engine
```

See:

```text
docs/RURO_PACKAGE_PORTABILITY_AND_CLEANUP_POLICY_v1.md
```

## 18. Cleanup And Archiving

The project should keep cleanup behaviour active, but it should be
archive-first, not delete-first.

Safe rule:

```text
If a generated artifact is replaced and may still be needed for provenance,
move or copy it to an archive location with timestamp metadata before writing
the replacement.
```

Do not auto-delete:

- raw data;
- EUROMOD releases;
- active MNL files without an archive;
- active estimation result folders;
- docs that explain current methods;
- canary reports tied to a run.

Prefer timestamped outputs for estimation and post-estimation. For deterministic
pipeline artifacts that use fixed names, document overwrite risk and archive the
old version first when needed.
