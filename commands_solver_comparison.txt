## EXECUTIVE SUMMARY

For your specification comparison tests, use this strategy:

STAGE 1 (Quick screening - 2-3 hours):
- Run SciPy L-BFGS-B for all 4 specs (fastest, ~15-30 min each)
- Identify which specs have better condition numbers
- Parallel run 2-3 simultaneously

STAGE 2 (Robustness check - 4-6 hours):
- Run GAMSPy CONOPT on the 2-3 best specs
- Compare results to SciPy
- If results agree closely → reliable
- If results differ significantly → identification problem confirmed

STAGE 3 (Optional validation - 2-3 hours):
- Run alternative solvers (IPOPT, KNITRO if available)
- Check convergence patterns

---

## WHY SCIPY IS FASTER FOR SMALL SPECS

### Parameter Count Effect
- **minimal_theta0.yaml:** 15 parameters
- **pooled_consumption.yaml:** ~12 parameters
- **pooled_leisure.yaml:** ~13 parameters
- **ultra_minimal.yaml:** ~7 parameters

### Computational Complexity
SciPy L-BFGS-B:
- Quasi-Newton method (approximates Hessian)
- ~1-2 iterations per function evaluation
- ~100-200 function evaluations typical
- Total: 30 sec - 2 min per run (with 6 demographic groups)

GAMSPy CONOPT:
- Newton method (exact second derivatives via autodiff)
- ~10-20 iterations (more careful)
- Each iteration may involve more overhead
- Total: 1-2 minutes per run

**Result:** SciPy ~5-10x faster for small problems, but GAMSPy is more reliable.

## SOLVER TRUST RANKINGS

### Tier 1: HIGH TRUST (Use for final results)

#### SciPy L-BFGS-B
**Pros:**
- Mature, widely tested (scipy since 2008+)
- Handles bounds correctly
- Gradient verification built-in
- Fast for small-medium problems
- Every academic paper uses it as baseline

**Cons:**
- Quasi-Newton (approximates Hessian) → less reliable Hessian diagnostics
- Can be sensitive to scaling
- May miss small numerical issues

**When to use:**
- Initial screening of specifications
- When you have weak identification (ill-conditioned)
- Comparing multiple specs quickly

**Example command:**
```bash
python scripts/enhanced/enh_RURO_estimate_FR.py \
  --mnl-base "Z:/hisham/EUROMOD-STORAGE/Data/processed/fr/2016/fr_2016_RURO_mnl" \
  --output-dir "outputs/estimates/fr/spec_tests/pooled_consumption_scipy" \
  --group joint \
  --solver scipy \
  --method L-BFGS-B \
  --maxiter 2000 \
  --spec-config "scripts/enhanced/estimation_spec_pooled_consumption.yaml" \
  --auto-timestamp \
  --verbose
```

#### GAMSPy CONOPT (Newton method)
**Pros:**
- Exact second derivatives (automatic differentiation)
- Newton method (quadratically convergent)
- **MOST RELIABLE Hessian diagnostics**
- Better for ill-conditioned problems
- Industry standard (GAMS/CONOPT widely used)

**Cons:**
- Slower than SciPy L-BFGS-B
- More overhead per iteration
- Requires GAMSPy installation
- CONOPT specific tuning may be needed

**When to use:**
- **After** finding promising specs with SciPy
- **For final results** where you need accurate Hessian diagnostics
- When comparing to published results (they probably used CONOPT)
- When standard errors must be accurate

**Example command:**
```bash
python scripts/enhanced/enh_RURO_estimate_FR.py \
  --mnl-base "Z:/hisham/EUROMOD-STORAGE/Data/processed/fr/2016/fr_2016_RURO_mnl" \
  --output-dir "outputs/estimates/fr/spec_tests/pooled_consumption_gamspy" \
  --group joint \
  --solver gamspy-conopt \
  --spec-config "scripts/enhanced/estimation_spec_pooled_consumption.yaml" \
  --auto-timestamp \
  --verbose
```

### Tier 2: MEDIUM TRUST (Use for sensitivity checks)

#### GAMSPy IPOPT (Interior Point)
**Pros:**
- Also provides exact second derivatives
- Different algorithm class (may find different local maxima)
- Good for highly constrained problems
- Used in many optimization packages

**Cons:**
- Interior point method (slower per iteration)
- Different convergence behavior than Newton
- May require fine-tuning barrier parameters

**When to use:**
- Check if CONOPT found a different local maximum
- If CONOPT is struggling, try IPOPT

**Example command:**
```bash
python scripts/enhanced/enh_RURO_estimate_FR.py \
  --solver gamspy-ipopt \
  --spec-config "scripts/enhanced/estimation_spec_pooled_consumption.yaml" \
  ...other args...
```

#### GAMSPy KNITRO (if available)
**Pros:**
- Very robust to scaling issues
- Can handle degeneracy well
- Good documentation

**Cons:**
- Commercial solver (may not be available)
- Expensive licensing
- Overkill for well-posed problems

## WHICH RESULTS TO TRUST: SCIPY vs GAMSPY

### Key Question: Do They Agree?

**Define "agreement":**
```
- Log-likelihood (LL) difference < 1% → Agree (same local maximum)
- LL difference 1-5% → Partial agreement (nearby local maxima, might both be valid)
- LL difference > 5% → Strong disagreement (one found wrong local maximum)
```

### Decision Tree

```
1. Run SciPy (fast screening)
   ↓
2. Does convergence look good? (iterations reasonable, gradients small)
   YES → Run GAMSPy CONOPT on same spec
   NO  → Problem may be ill-defined (high cond #)
   ↓
3. Compare SciPy LL vs CONOPT LL
   ↓
   ├─ Within 0.1% (< 10 LL units)
   │  └─> Both solvers agree → TRUST BOTH
   │     Use SciPy for speed, confirm with CONOPT
   │
   ├─ Within 1% (< 100 LL units)
   │  └─> Close agreement → CAUTIOUSLY TRUST
   │     GAMSPy CONOPT is more reliable
   │     Investigate why they differ
   │
   └─ Differ by >1%
      └─> DISTRUST BOTH
         Check: ill-conditioning, local maxima, scaling issues
         Run IPOPT as tiebreaker
```

### Example Interpretation

**Your recent run (minimal_theta0):**
- LL = -6954.24 (GAMSPy CONOPT)
- If SciPy gives LL ≈ -6954.2 to -6954.3 → Agree perfectly ✓
- If SciPy gives LL ≈ -6960 → Significant disagreement ✗

## YOUR SPECIFIC QUESTION: SciPy vs GAMSPy for Identification

**Answer:** For identifying the source of ill-conditioning, use BOTH:

1. **SciPy first:** Find which specs have better condition numbers (numerical Hessian approximation)
2. **GAMSPy CONOPT second:** Confirm the condition numbers are real (exact Hessian), get final diagnostics

The smallest-eigenvalue directions come from GAMSPy's exact Hessian, so that's your reliable diagnostic. But SciPy gets you there 10x faster for initial screening.
