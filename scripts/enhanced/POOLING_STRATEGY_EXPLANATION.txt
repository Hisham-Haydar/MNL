================================================================================
POOLING STRATEGY EXPLANATION
================================================================================

CRITICAL DISCOVERY: The Parser Has Fixed Architecture
======================================================

The estimation_spec_parser.py has HARDCODED 4-GROUP architecture that ALWAYS creates:

1. Singles Male (_sm suffix):        beta_l0_sm, beta_c_sm, theta_l_sm, theta_c_sm
2. Singles Female (_sf suffix):      beta_l0_sf, beta_c_sf, theta_l_sf, theta_c_sf
3. Couples Male (_m suffix):         beta_l0_m, theta_l_m (NO beta_c for individuals)
4. Couples Female (_f suffix):       beta_l0_f, theta_l_f (NO beta_c for individuals)
5. Couples Household (no suffix):    beta_c, theta_c

This is defined in estimation_spec_parser.py lines 516-598 and CANNOT be changed
via YAML configuration. The parser does NOT support reducing this to arbitrary
group structures.

================================================================================
HOW POOLING WORKS WITH THIS ARCHITECTURE
================================================================================

Since we cannot change the parameter creation, we implement "pooling" through
INITIALIZATION and OPTIMIZATION CONSTRAINTS.

The approach:
1. Initialize potentially redundant parameters to the SAME VALUE
2. Let optimizer decide if they should diverge
3. If optimizer leaves them equal (low gradients in divergence direction),
   pooling is validated

Example: POOLED CONSUMPTION
----------------------------

Parser creates:  beta_c_sm, beta_c_sf, beta_c (3 parameters)
We initialize:   beta_c_sm: 1.0, beta_c_sf: 1.0, beta_c: 1.0 (all equal)
Optimizer sees:  3 parameters with identical initial values
Result:          If all stay ~1.0, consumption is effectively pooled

Interpretation:
- If gradient pushes them to diverge significantly: pooling hypothesis REJECTED
- If they stay nearly equal: consumption utility does NOT differ by group
- Data suggests log(C) utility matters equally for all demographic groups


Example: POOLED LEISURE BY GENDER
----------------------------------

Parser creates:  beta_l0_sm, beta_l0_sf, beta_l0_m, beta_l0_f (4 parameters)
We initialize:   beta_l0_sm: 0.35 (male), beta_l0_sf: 1.01 (female),
                 beta_l0_m: 0.35 (male), beta_l0_f: 1.01 (female)
Optimizer sees:  4 parameters, but sm=m (by value) and sf=f (by value)
Result:          If sm stays ≈ m and sf stays ≈ f: leisure pooled by gender
                 (singles and couples have same gender-based preferences)

Interpretation:
- If singles diverge from couples: marital status matters for leisure
- If singles track couples: marital status DOESN'T matter for leisure
- Useful test of whether singles/couples distinction is real

================================================================================
KEY INSIGHT: INTERPRETATION OF EQUAL ESTIMATES
================================================================================

When optimizer KEEPS parameters equal despite independent parameter structure:

EQUALS OR NEARLY EQUAL:
  ┌─ Data cannot distinguish parameter values
  ├─ Pooling constraint is NOT binding during optimization
  ├─ Suggests parameter is unidentified or nearly unidentified
  └─ Removing parameter (true pooling) would improve condition number

DIVERGE SIGNIFICANTLY:
  ├─ Data has strong information about difference
  ├─ Pooling constraint IS binding (cost of keeping equal)
  ├─ Parameter difference is identified
  └─ Parameter should remain separate

This is an INDIRECT way to test identification:
- Each spec is essentially testing whether constraints are binding
- Binding constraints = unidentified parameters
- Non-binding constraints = well-identified differences
